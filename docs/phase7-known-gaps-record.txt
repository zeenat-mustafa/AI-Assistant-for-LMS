Phase 7 — Known Gaps Record
============================
Gaps accepted by design (or found and deliberately deferred) during Phase 7
(RAG + memory-aware student chatbot + in-chat quizzes). Not bugs to "fix"
without being asked. 7.1-7.5's gaps are recorded in CLAUDE.md's Phase 7
status section; this file starts at 7.6. See docs/phase5-known-gaps-record.txt
for the previous phase.

  FOUR EXISTING CHROMA ENTRIES HELD RAW BASE64 IMAGE NOISE (found in 7.6
  review; deferred at the time, re-embedded afterwards). Two markdown cells in each of these
  unsolved notebooks (both session 4, "Week 2 Day 2") are a single embedded
  image and nothing else:

    dataframe_basics.ipynb  (unsolved_files.id=10)
      notebook:10:55  (cell 56, 1-indexed)  80,886 chars  group_by_cities.png
      notebook:10:62  (cell 63, 1-indexed) 140,038 chars  split_apply_combine.png
    pandas_group_by.ipynb   (unsolved_files.id=11)
      notebook:11:8   (cell 9, 1-indexed)   80,886 chars  same image
      notebook:11:15  (cell 16, 1-indexed) 140,038 chars  same image

  7.2 embedded them without any error (unsolved_files.embedded=1,
  embedding_error NULL). The stored Chroma DOCUMENT is the full raw
  `![...](data:image/png;base64,...)` string, and the VECTOR represents only
  its first 256 tokens (all-MiniLM-L6-v2's max_seq_length silently truncates
  the rest) — i.e. base64 noise. Functionally near-meaningless vectors for
  those four chunks: not a security leak (no answer or student data is in
  them), but a real retrieval-quality gap. They are very unlikely to clear
  the 0.35 similarity threshold for a real question; if one ever did, 7.5
  would put the raw base64 document into the chat prompt and its citation
  snippet.

  THIS WAS A CROSS-FEATURE EXPOSURE; WHEN 7.6 WAS COMMITTED, ONLY 7.6's SIDE
  OF IT WAS CLOSED. (Paragraph kept as written at 7.6 commit time.)
  7.6's topic-mode fix stops quiz generation from ever surfacing these four
  entries, but 7.5's student-chat retrieval (POST /student-chat/stream)
  reads Chroma's stored document field directly with no equivalent
  protection — if a student's chat question retrieved one of these entries
  today, the raw base64 would still reach the chat prompt. Do not read this
  entry as fixed: the recommended backfill below is what resolves both
  consumers (quiz and chat) at once, and it has not been run.

  Root cause fixed going forward (7.6): extract_notebook_structure() and
  extract_notebook_structure_from_bytes() gained an opt-in
  strip_images=True, which replaces embedded base64 images with
  "[image omitted]". It is on for the upload embedding flow
  (routers/assignments.py) and scripts/backfill_embeddings.py, so no future
  upload or backfill embeds image payloads. It is deliberately OFF (default)
  for grading and rubric generation (evaluator.py, rubric.py), whose prompts
  stay byte-identical; six real student submission notebooks in session 4
  contain these same images, and changing grading input would need its own
  re-verification pass. The quiz (7.6) is not affected by the stale entries:
  it reads notebook text from the source files with strip_images=True, and
  topic mode uses the re-read cell text, never Chroma's stored document.

  RECOMMENDED FOLLOW-UP (not done): once the 7.6 fix is committed, re-embed
  just those two files with strip_images=True. Note that
  scripts/backfill_embeddings.py only processes UnsolvedFile rows with
  embedded=False, so re-running it as-is does nothing for these files — the
  follow-up must first set embedded=False for ids 10 and 11 (after a
  sqlite3 backup-API DB backup), then run the script. Chunk ids are
  deterministic, so the upsert overwrites the four entries in place rather
  than duplicating them.

- A MULTI-SESSION QUIZ CAN MIX TOPICALLY UNRELATED MATERIAL INTO ONE
  NONSENSICAL QUESTION. Real example from 7.6's re-verification: a
  multiple_sessions quiz over sessions [4, 8] (pandas notebooks + the
  AI-agents lecture) produced, as Q2: "In the Split-Apply-Combine procedure
  demonstrated with Pandas GroupBy objects, what primary role does
  short-term memory or tracking play when compared against the agent
  execution loop discussed in later sessions?" Its source_citation was
  correct (week 10_day1.pptx, slide 10) and its marked answer is correct for
  that slide, but the question itself blends two unrelated topics and makes
  no sense.

  This is a real, disclosed quality limitation of combining material from
  topically unrelated sessions in one quiz — not a leak (nothing from a
  completion gap is revealed), and not something to be fixed by altering
  the already-signed-off quiz-generation prompt. The other 4 questions in
  that quiz, and every single-topic quiz verified in 7.6, did not show it.

- REPEAT QUIZZES ON A SMALL NOTEBOOK ARE VERY SIMILAR. Material sampling
  only varies a quiz when a scope's material exceeds the 40k-character
  budget. After the heuristic_hint and hint-cell filters, Week 10_Lab3.ipynb
  has about 2,200 characters of usable text, all of which is sent every
  time, so repeat quizzes on it ask near-identical questions. Accepted
  trade-off of excluding hint cells (7.6 review).

- THE HINT-CELL FILTER EXCLUDES ANY CELL CONTAINING THE WORD "hint"/"hints".
  One whole-word, case-insensitive rule (quiz_generator.is_hint_cell), chosen
  over heading/label patterns because every real hint note found contains the
  word and the one real 💡-non-hint ("💡 Inspiration:") does not. It will
  also drop a cell using the word in ordinary prose ("a hint of
  seasonality"); no real course notebook does this today. Quiz-only — it
  does not change what embedding, chat, or grading see.

- QUIZ CITATIONS SHOW NOTEBOOK CELLS 1-INDEXED ("cell 7"); 7.5's student-chat
  citations return the raw 0-based cell_index. Known, accepted cosmetic
  inconsistency; 7.5 deliberately not changed.

=== PRE-DEMO PRIORITY: SOLUTION CONTENT IS IN THE RETRIEVAL CORPUS ===

- 7.3's PREMISE DOES NOT HOLD FOR THIS CORPUS — A REAL LEAKAGE VECTOR, NOT
  A HALLUCINATION. Affects: app/routers/assignments.py
  _embed_unsolved_file_cells (7.2), scripts/backfill_embeddings.py,
  app/services/embeddings.retrieve, app/routers/student_chat.py (7.5).
  Needs backend: YES. Priority: before the demo.

  7.3 was signed off on "unsolved files structurally never contain the
  solution, so the only risk is the model generating one". 7.2's embedding
  code encodes the same assumption: "a TODO placeholder or scaffolding
  comment is embedded as-is since it contains no answer". That holds WITHIN
  one notebook but breaks whenever a later lab carries an earlier lab's
  solution forward as GIVEN content — an ordinary way to sequence a
  multi-week course. This is a pipeline-design gap, not a fluke of two files.

  Evidence (read directly from the notebook JSON / DB / Chroma, zero LLM
  calls):
    - week10_day1_lab.ipynb (unsolved_files.id=21, session 7), cells[22] is
      the graded gap "Implementing the core multi-step ReAct agent loop in
      run_agent (Cell 23)", 2.5/10 of its cached rubric:
        for step in range(max_steps):
            # your loop body here — extract function_calls, branch on
            # empty/non-empty, execute, resend
            pass
    - Week10_Day2.ipynb (unsolved_files.id=17 session 5, id=19 session 6,
      id=22 session 7 — byte-identical cells) cells[11]: "Paste in the
      `run_agent` function you built yesterday (or use the version below if
      you'd rather start from a clean copy — it's identical to the Day 1
      Appendix solution)." cells[12]: "# GIVEN — carried over from Day 1
      (Appendix solution, in case you don't have your own copy handy)"
      followed by the COMPLETE working loop body. cells[21] (run_agent_v2) is
      a second complete copy of the same loop with a single line marked
      "🔧 TODO" — not labelled GIVEN, so a label-based filter would miss it.
    - All are embedded: Chroma ids notebook:22:12, notebook:17:12,
      notebook:19:12 present (e.g. metadata {'source_type': 'notebook',
      'source_file_id': 22, 'cell_index': 12, 'cell_type': 'code',
      'session_id': 7}); file 21 has 41 chunks, 17/19/22 have 44 each.
    - Real retrieve() with 7.5's own answer settings (session_id=7, top_k=5,
      min_similarity=0.35) put the solution cell into the prompt for
      ordinary student phrasings: "My run_agent loop never stops. How should
      I extract function_calls from response parts and send the
      function_response parts back?" -> notebook 22 cell 12 at rank 2
      (0.6577); "for step in range(max_steps): parts =
      response.candidates[0].content.parts" -> rank 1 (0.5582); "How do I
      build function_response_parts with types.Part.from_function_response
      inside the agent loop?" -> rank 2 (0.6046). "Can you show me the
      appendix solution for run_agent?" -> the pointer cell 11 at rank 1
      (0.7246).
    - Corpus-wide audit of all 22 unsolved_files: 54 cells matched a broad
      GIVEN/carried-over/appendix/solution keyword scan; 30 were false
      positives (ordinary prose, "for a given model" TODO prompts, exercise
      questions); 24 were real (20 GIVEN code cells + 4 pointer/appendix
      cells). Cross-file correspondence to another file's graded gap:
        FULL SOLUTION  Week10_Day2 cells 12 and 21 (ids 17, 19, 22)
                       -> week10_day1_lab cell 22 (2.5/10)
        REAL POINTER   Week10_Day2 cell 11 (ids 17, 19, 22);
                       week10_day1_lab cell 20 ("check the Appendix")
        PARTIAL        week10_day1_lab cell 15 GIVEN get_weather (sample
                       lahore/karachi values) -> Week 10_Lab3 cell 10
                       weather-dict gap (1.0/10)
        NONE           the other GIVEN cells (Day 2 cells 9/10/32/41, Day 1
                       cells 16/17, Lab_Day4 cells 6/16)
      Also found outside GIVEN cells, same exposure inside session 7: the
      week10_day1_lab cell 22 scaffold line `tool_registry = {"get_weather":
      get_weather}` is the literal answer to half of Week 10_Lab3 cell 25's
      gap, and week10_day1_lab cell 27's "hint: Python's `eval()` works fine"
      gives away Week 10_Lab3 cell 15's calculator gap (the known eval leak,
      reached through another file).
      Affected: 3 row pairs with a full solution (17->21, 19->21, 22->21;
      only 22->21 share a session today), 1 row pair with partial/answer-level
      leakage (21->20, session 7), across 2 distinct lab sequences in one
      course week. Several pairs -> the embedding/retrieval pipeline needs to
      change, not one file's content.

  The exact mechanism that has to change or be constrained: retrieval
  scores on the CURRENT QUESTION TEXT ALONE — student_chat.py:160
  `retrieve(body.question, session_id=resolution.session_id,
  top_k=ANSWER_TOP_K, min_similarity=ANSWER_MIN_SIMILARITY)`; conversation
  history is never used for retrieval — and embeddings.retrieve filters
  ONLY by `where = {"session_id": session_id}`, with no per-file exclusion.
  Every embedded unsolved cell in a resolved session (including another
  lab's carried-forward solution) is eligible material for any question.

=== BACKEND LIMITATIONS THE 7.7 FRONTEND SURFACES ===

- NO LECTURE DELETE ENDPOINT. Affects: /sessions/{id}/lectures
  (routers/lectures.py). A 409 filename collision has no in-app resolution;
  the UI shows the backend's detail verbatim plus "Lecture files can't be
  removed in the app, so rename your file and upload it again." Why: 7.1
  deliberately mirrored ResourceFile's no-delete precedent. Needs backend:
  yes. (A real verification artefact — lecture_files row 3, a 44-byte
  corrupt upload — had to be removed directly from the DB in the 7.7
  closeout under Standing Rule #10.)

- NO THREAD-LIST OR MESSAGE-HISTORY ENDPOINT. Affects:
  /student/sessions/[id]/chat; backend conversation_threads/messages (7.4).
  The on-screen transcript starts empty on every visit even though backend
  memory persists (verified: after a reload, the assistant recalled both
  earlier questions verbatim). The page says so in one line; nothing is
  cached client-side. Why: 7.5 exposed only POST /student-chat/stream.
  Needs backend: yes (a read endpoint for a student's own thread).

- LectureFileRead CARRIES NO SIZE, SLIDE COUNT, CHUNK COUNT, OR EMBEDDED
  FLAG. Affects: GET /sessions/{id}/lectures (schemas/lecture_file.py). The
  UI shows only filename, upload date, content_type and extraction status.
  Why: 7.1's schema. Needs backend: yes.

- CITATION snippet IS CAPPED AT 200 CHARACTERS. Affects: student_chat.py
  SNIPPET_CHARS. "Show preview" can only ever show a truncated preview and
  says so. Why: 7.5 keeps SSE payloads small. Needs backend: yes for more.

- NOTEBOOK cell_index IS 0-INDEXED AND SURFACED RAW. Affects: citations
  event; citation-list.tsx. The UI shows "Cell 0" and adds a legend line
  rather than +1, so values cross-check against the notebook JSON. Needs
  backend: no (display choice), but see the next-but-one entry.

- THE CITATION source FIELD IS slide_text / notes, NOT A FILENAME. Affects:
  lecture citations (ChunkSource enum). 7.7 renders it as part of the
  locator ("Slide 17 · slide text"); never use it as a filename fallback.
  Needs backend: no.

- QUIZ source_citation IS A SERVER-BUILT STRING WITH 1-INDEXED CELLS,
  inconsistent with chat citations' 0-indexed structured fields. Affects:
  quiz_generator._notebook_citation. Rendered verbatim as "Source: ...".
  Needs backend: yes to unify.

- QUIZ RESULTS CARRY NO EXPLANATION TEXT. Affects: QuizResultOut. A wrong
  answer is marked correct/incorrect with the correct option shown, but not
  explained. Why: 7.6's schema. Needs backend: yes.

- ABANDONED QUIZ ATTEMPTS ACCUMULATE, UNLISTED. Affects: quiz_attempts; GET
  /quiz/history lists submitted attempts only. Navigating away from a
  generated, unsubmitted quiz calls nothing and leaves the row: 9 exist now.
  Needs backend: yes (listing or cleanup).

- extraction_error EXPOSES THE SERVER'S ABSOLUTE STORAGE PATH. Affects:
  lecture_extraction.extract_pptx_content -> LectureFileRead. Real example
  shown to the instructor: "File does not appear to be a valid .pptx
  package (corrupted or not actually PowerPoint format): E:\Final
  Project-AI\AI-Assistant-for-LMS\backend\storage\sessions\8\lectures\
  downloaded_lecture.pptx". The frontend deliberately renders it verbatim
  (hiding it would hide a real error). Suggested fix (backend): return the
  basename or a stable error code instead of the resolved absolute path.
